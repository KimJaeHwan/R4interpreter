# Python 남은 핵심 범위 실험

## 한눈에 보는 결과

고정 CPython 바이너리의 `branchCall(x) → addFive(x)`에서 숫자 구간과 이웃 구간을 호출자 쪽 증거와 연결했다. 원본 `x=252`와 새 전체 추적 `x=254`는 **할당 경로 146명령 + 이웃 구간 94명령**, 새 `x=251`은 **캐시 경로 116명령 + 이웃 구간 94명령**에 동결 요약을 적용했다. 세 실행 모두 입력 분기의 첫 235명령, 호출 인자 전달의 세 국소 구간, 두 동결 전이, 바깥 반환의 94명령을 확인했다. 각각 `257`, `259`, `256`인 정수 객체 포인터가 부모 결과 슬롯에서 호출자 결과 슬롯까지 전해졌다. 앞쪽 총 683명령 중 검사한 창 사이의 명령은 여전히 별도 요약이 없다. 이 결과는 전체 Python 함수의 완전한 복원이 아니다.

| 의무 | 새로 확인한 것 | 아직 모르는 것 |
|---|---|---|
| 분기·경로 | 원본 `252`의 고정 진입 상태에서 `X=252..256`이면 선택한 240명령 안의 P-code 조건분기 33회 모두 반대쪽이 `unsat`. `251`로 넓히자 `0x5e978a`에서 반대쪽 후보가 `sat`; 독립 실행이 이를 확인하고 캐시 경로 요약에 합격 | 다른 초기 메모리·allocator 상태, 다른 앞쪽 경로, 호출 실패·예외 경로. 이 구간의 32개 네이티브 조건분기 중 하나에 P-code 내부 분기가 추가되어 33회 |
| 호출·반환 | `x=251,252,254`의 부모 로컬 → 호출 인자 → 자식 로컬 → 덧셈 피연산자와 요약 두 개 → 부모 반환 슬롯 → 호출자 슬롯을 연결 | 창 사이의 모든 명령 의미와 다른 호출 경로. 바깥 94명령은 대상 추적에 P-code를 다시 실행했으므로 동결 요약의 재사용 범위에 포함되지 않음 |
| 객체·수명 | 두 새 객체 모두 4개 필드 쓰기와 쓰기 전 객체 주소 읽기를 관측 | 실제 `Allocate`·`Free`, 할당 범위·세대, 이전 해제·재사용, 소유권, 실패 계약. 모두 `unknown` |

## 분기를 어떻게 판정했나

원본 `252`의 네이티브 240명령을 P-code로 재생하고, 입력 객체의 32비트 digit만 `X`로 바꿨다. 각 조건 분기에서 **그 분기보다 앞서 지나온 조건만** 더한 후 반대 방향을 질의했다. `252..256`에서 33번 모두 `unsat`인 것은 이 고정 진입 환경과 이전 경로에서 반대쪽으로 갈 수 없다는 뜻이다. 현재 분기의 조건까지 먼저 넣고 반대쪽을 묻는 자기모순 계산은 사용하지 않았다. 입력 범위가 `251..256`이면 첫 반대 경로 모델은 `X=251`, PC `0x5e978a`였다. 새 `251` 전체 추적은 그 지점에서 `0x5e978c`로, 원본 `252`와 새 `254`는 `0x5e97b0`으로 진행했다. `251`에는 **별도로 동결한 캐시 경로 요약**을 적용했다. 갈라진 뒤 할당 경로 요약을 계속 적용한 것이 아니다. 다만 `251`의 반대 edge 관측이 원본 `252` 환경의 모든 앞선 상태까지 동일하게 실현했다는 뜻은 아니다. 이는 모든 Lua/Python/JavaScript 분기나 전체 입력 공간의 완전성 증명이 아니다.

## 연결과 효과의 범위

입력 쪽 첫 235명령에서는 각 추적의 고정 환경 아래 `rsi = ZeroExt(32, X)`를 확인했다. 그 뒤 부모의 로컬 객체 포인터가 호출 인자 슬롯으로 옮겨지고, 자식의 인자 슬롯과 덧셈 왼쪽 피연산자로 전달되는 세 창을 각각 P-code로 확인했다. 호출 인자 값 또는 자식 슬롯 주소를 바꾼 **국소 바인딩 검사**는 거부했다. 첫 숫자 구간의 계산 상태와 바이트 메모리는 이웃 구간으로 넘겨 **재초기화 없이** 동결 요약을 적용했다. 이어 부모 결과 슬롯을 바이트 단위로 확인했다. 바깥 반환 94명령의 진입 GPR·플래그·FS/GS를 이전 요약의 종료 상태와 대조하고, FS/GS 보존과 대상 P-code의 37회 읽기·순서 있는 18개 쓰기·종료 GPR 16개·플래그 5개를 검사했다. 부모 결과 슬롯, 진입 GPR·플래그·FS base를 훼손한 부정 사례도 거부했다.

여기서 앞쪽 683명령 전체가 상징적으로 이어진 것은 아니다. 세 국소 창의 시작 메모리는 각 추적의 첫 읽기 값에 고정되어 있고, 창 사이의 수명·메모리 변화를 하나의 계약으로 증명하지 않았다. 바깥 반환은 새 추적에서도 재실행한 검증이므로 별도 동결 요약이라고 부르지 않는다. 기존 두 요약의 네이티브 쓰기와 바깥 반환의 18개 쓰기를 제거하지 않았다. 입력값 `X+5`라는 값 IL은 이 조건부 경로를 읽기 쉽게 나타내지만 그 자체로 객체 할당이나 전체 함수 효과를 나타내지 않는다.

할당 쪽은 `0x5932f3 → 0x5e9710` 내부 호출을 관측했고, 결과 객체의 `+0,+8,+16,+24` 필드가 쓰였다. 그러나 `+0` 주소를 필드 쓰기 전에 읽었으며, 앞선 자유 목록 상태와 실제 할당 범위는 모른다. 따라서 포인터가 새로 보이고 필드가 채워졌다는 이유만으로 공통 IL에 `Allocate` 또는 `Free`를 넣으면 안 된다. 별도 제한 풀 fixture에서 입증한 수명 계약도 이 CPython 경로에 전용하지 않았다.

## 산출물과 재현

세부 PC·해시·부정 사례·미해결 의무는 [기계 판독 결과](python_remaining_scope_result.json)에 있다. 두 새 전체 추적은 `artifacts/next_scope_py_251.json.gz`, `artifacts/next_scope_py_254.json.gz`에 보존했다.

```bash
cd experiments/interpreter-expression
../vm-transition-testbed/.venv/bin/python probe_python_remaining_scope.py
```

새 전체 추적은 고정 실행기와 같은 fixture에서 다음처럼 다시 수집할 수 있다 (`INPUT`에 `251` 또는 `254`를 넣는다).

```bash
../vm-transition-testbed/.venv/bin/python trace_cross_full_flow.py \
  --watch-bridge --through-return python /usr/bin/python3.13 \
  artifacts/next_scope_py_${INPUT}.marker.json \
  artifacts/next_scope_py_${INPUT}.json.gz -I -S \
  artifacts/cross_python_fixture.cpython-313.pyc \
  --mark artifacts/next_scope_py_${INPUT}.marker.json --native-sync "$INPUT"
```

남은 우선 작업은 앞쪽 창 사이의 메모리·호출 계약, 분기 이후 다른 경로와 예외 종료, CPython allocator의 실제 할당·해제 계약이다. 이들이 없으면 읽을 만한 전체 로직 출력은 구멍을 표시한 조건부 부분 결과로 유지해야 한다.
