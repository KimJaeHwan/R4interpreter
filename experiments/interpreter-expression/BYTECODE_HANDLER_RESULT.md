# 바이트코드 명령과 Lua VM 네이티브 처리 구간 연결

저장된 `lua_chunk.luac`와 동일한 실행기에서 입력 `9`, `0`을 각각 실행했다. `luaV_execute`의 명령 추적에서 **32비트 명령 읽기(`LOAD`) → 하위 7비트로 점프 테이블 인덱스 생성 → 간접 분기(`BRANCHIND`)**를 찾아, 읽힌 값과 후속 네이티브 주소를 묶었다. 읽힌 세 연속 값은 `.luac` 파일의 바이트 오프셋 `39`부터 한 번만 나타난다. 런타임의 다음 읽기 주소 차이로 바이트코드 인덱스를 계산하고 파일의 해당 4바이트 값과 다시 대조했다. Lua opcode 이름이나 Lua 소스는 이 대응에 사용하지 않았다.

| 실행된 바이트코드 인덱스 | 파일 바이트 오프셋 | 수치 opcode (하위 7비트) | 간접 분기 후 네이티브 진입 주소 | 관측 |
|---:|---:|---:|---:|---|
| 0 | 39 | 81 | `0x415bb0` | 두 입력에서 같은 경로 진입 |
| 1 | 43 | 11 | `0x416ac8` | 두 입력에서 같은 경로 진입 |
| 2 | 47 | 21 | `0x4164b8` | 실행 구간에 `0x417ce7`의 `INT_ADD` 포함 |
| 4 | 55 | 70 | `0x415820` | 두 입력에서 같은 경로 진입 |

각 실행에서 관측된 VM의 간접 분기 4개 모두 앞선 바이트코드 읽기에 대응됐다. 인덱스 `3`의 파일 명령 값은 존재하지만 이 두 실행에서 별도로 읽히지 않았다. 건너뛴 이유나 해당 명령의 의미는 이번 관측만으로 확정하지 않는다. 동일한 바이트코드 파일에서 입력 `9`와 `0`의 **인덱스·명령 값·분기 주소·구간별 실행 명령 수가 모두 같았다.**

인덱스 `2`의 구간 안에서 메모리 값 `9`와 레지스터 값 `7`이 `16`으로 더해져 저장되는 것을 첫 입력에서 확인했다. 두 번째 입력에서는 같은 네이티브 명령이 메모리 값 `0`과 `7`을 더해 `7`을 저장했다. 실제 실행 출력도 각각 `16`, `7`이었다. 따라서 **바이트코드 위치 2 → 숫자 opcode 21의 분기 → 네이티브 덧셈 → P-code `INT_ADD`**까지 두 실행에서 연결했다.

## 적용 범위와 다음 단계

이 결과는 **현재 ELF와 바이트코드, 두 입력에서 관측한 첫 VM 호출**에 대한 대응이다. opcode 21의 언어 수준 이름이나 모든 경로의 의미를 확정하지 않는다. 실행기 입력이 VM 안에서 읽힌 메모리 값이 되기까지의 전체 출처와 경로 guard도 아직 연결되지 않았다. 다음 단계에서 실행기 진입부터 VM의 해당 메모리 쓰기까지 추적하고, 별도 입력으로 일반식의 적용 범위를 확인한다.
