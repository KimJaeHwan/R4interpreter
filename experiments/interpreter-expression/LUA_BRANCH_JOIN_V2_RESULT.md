# Lua 분기 뒤의 인자·결과 연결: 7개 실행

이번 연구 단위는 기존의 Lua 7개 입력 추적에서 같은 분기 명령의 바이트코드 문맥을 직접 확인하고, 두 갈래가 호출한 산술 핸들러에 들어가는 값과 결과를 연결했다. [증명 코드](prove_lua_branch_join_v2.py)는 기존 추적·ELF·Ghidra P-code Bundle과 앞 단계의 증거를 다시 읽어 [결과](lua_branch_join_v2.json)를 만든다. `daasdmlkas` 저장소는 수정하지 않았다.

## 확인한 값의 흐름

입력 `X`는 각 실행에서 파싱된 64비트 인자와 하드웨어 감시를 거친 Lua VM 소스 슬롯에 묶인다. 동일 추적의 바이트코드 읽기 오프셋 51, 수치 opcode 61, 간접 분배 대상 `0x415ee0`이 네이티브 분기 `0x415f30`보다 앞선다. 분기 자체의 **taken 조건은 `X == 0`**이다. 대상 분기의 관측 edge를 전제에서 빼고, 각 실행의 이전 guard 아래 양쪽 입력 가능성과 조건식 동치를 SMT로 확인했다.

| 입력 | 관측 분기 | 호출 바이트코드 오프셋 | 산술 핸들러의 인자 | 결과 |
| --- | --- | ---: | --- | --- |
| `0` | `X == 0` | 67 | `5` | `10` |
| `9` | `X != 0` | 83 | `X = 9` | `14` |
| `1` | `X != 0` | 83 | `X = 1` | `6` |
| `-1` | `X != 0` | 83 | `X = 2^64-1` | `4` |
| `INT64_MAX` | `X != 0` | 83 | `X = 2^63-1` | `2^63+4` |
| `INT64_MIN` | `X != 0` | 83 | `X = 2^63` | `2^63+5` |
| `42` | `X != 0` | 83 | `X = 42` | `47` |

두 경로 모두 같은 바이트코드 오프셋 111, 수치 opcode 21, 네이티브 산술 핸들러 `0x4164b8`에 도달한다. 그 진입 시점의 `RBX`를 **각 실행의 프레임 기준점**으로 잡으면 인자 8바이트는 `RBX+0`, 관측한 정수 태그 1바이트는 `RBX+8`, 결과 저장 8바이트는 `RBX+16`이다. 절대 주소는 실행마다 다르다. P-code 재생에서 기호 입력에 대해 `RBX`가 관측된 프레임 기준점과 같음도 증명했다. VM 소스부터 산술 핸들러 진입 직전까지 재생하여 `인자 = (X == 0 ? 5 : X)`와 태그 `3`을 증명했다. 기존 소스부터 결과 저장까지의 P-code 증명을 다시 실행하고, 결과가 `(인자 + 5) mod 2^64`와 일치하는지도 확인했다. `-1`, 최대값, 최소값은 부호 있는 무한 정수가 아니라 **BV64의 순환 연산**으로 해석한다.

읽을 수 있는 **값 골격**은 다음과 같다.

```text
if X == 0:
    argument = 5
else:
    argument = X
result = (argument + 5) mod 2^64
```

이는 원본 Lua 코드를 역컴파일한 결과가 아니다. 일곱 개의 관측 경로에서 재생한 네이티브 효과 중 입력·인자·결과에 관한 증명이다. 바이트코드의 다음 **캡처된** 읽기가 즉시 다음 명령이라는 뜻도 아니다. 같은 핸들러 주소와 프레임 기준 슬롯 대응은 값이 만나는 지점의 근거지만, 모든 레지스터·힙·객체 수명까지 동일한 VM 상태로 합류했다는 증거는 아니다.

## 제어 경로 작업 목록의 변화

앞 단계의 720개 발생 목록은 그대로 둔다. 기존 공통 표현과 frontier 진행 지도를 원본에서 재구축해 저장본과 전체 비교했다. 그중 서로 반대 방향이 관측된 Lua 5개 발생에 같은 추적의 바이트코드 문맥과 개별 조건 증명을 추가하고, occurrence ID별 분류를 다시 집계했다. 기존 Python 4개와 Lua 2개를 합친 **바이트코드 문맥 확인 및 조건 증명 발생은 6개에서 11개**가 됐다. 반대 방향 미해결 557개, 정상 반환만 관측하고 예외 경로가 미해결인 호출 61개, 완전한 핸들러 대체 출구 집합 **0개**는 변하지 않는다. 숫자는 전체 프로그램의 분기 개수가 아니라 선택한 네이티브 작업 목록의 발생 수다.

검증은 두 층이다. 결과 JSON의 fetch·occurrence·프레임 슬롯·태그·인자·결과·합류 위치·BV64 표기를 바꾸면 원본에서 재계산한 보고서와 달라져 거부된다(8개). 실제 네이티브 기록에서 인자·태그·결과의 write 또는 callee frame 기준점을 바꿔도 증명 경로가 거부한다(4개). 기존 P-code 증명의 source-slot witness 및 잘못된 native successor 부정 검증도 입력별로 다시 실행한다.
