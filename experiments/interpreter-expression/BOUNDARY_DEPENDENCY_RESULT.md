# 관측 경로의 분배 경계와 의존성 감사

## 이번 판정

앞선 값 슬라이스는 명령 안의 P-code를 모두 역순으로 읽었다. `cmov`처럼 조건에 따라 마지막 대입을 건너뛰는 명령에서는 실행되지 않은 정의를 선택할 수 있었다. 이번에는 실제 레지스터·플래그·메모리 관측값으로 **명령 한 개의 P-code 경로**를 재생하고, 선택한 조건을 증명 의무로 남겼다. 지원하지 않는 내부 흐름은 `unknown`으로 유지한다.

| 대상 | 관측 경로의 결과 | 해석 |
|---|---|---|
| Lua 입력 42의 281명령 구간 | 선택 연산 545개, 기록된 내부 흐름 미지원 0건 | 현재 sink의 구조적 의존 목록. 별칭 부재·효과 삭제 증명은 아님 |
| Python 입력 42의 987명령 구간 | `cmov` 조건 3개 재생, 실행되지 않은 P-code 2개 건너뜀. 선택 연산 1,759→1,755개, 구조적 미해결 0건 | 관측 경로의 명령 내부 정의를 바로잡음. 임의 입력의 경로 보장은 아님 |
| JavaScript 입력 42의 29,446명령 구간 | `cmov` 조건 64개 재생, 연산 35개 건너뜀. 선택 연산 80,192→80,154개 | 4,228건은 **남음**: `rep` 4,189, `lock` 20, `bsf` 2의 내부 흐름과 AVX-512 `CALLOTHER` 11, 접근 모드 누락 6 |

기존 1/1/18이라는 미해결 묶음 수와 새 0/0/4,228은 같은 분류 체계가 아니다. 기존은 모든 선택된 일반 분기까지 “명령 내부 제어” 한 묶음으로 세었고, 새 결과는 실제 내부 분기마다 미지원 흐름을 기록한다. **0건은 값·주소·효과의 전역 폐쇄를 뜻하지 않는다.** [의존성 감사 결과](observed_dependency_audit_result.json)에 근거와 남은 항목을 기록했다.

`cmov`의 건너뛴 목적 레지스터와 실제 대입한 목적 레지스터의 종료값, 다음 명령 주소, 입력 플래그를 각각 변조한 네 경우도 모두 `unknown`이다. P-code 경로를 택할 때 관측 종료 상태 전체와 정상 fall-through를 확인한다. 이는 모델링한 스칼라 레지스터·플래그에 대한 검사이며, 미모델링 효과까지 없다는 주장은 아니다.

## 경계 후보 생성과 재사용

추적에서 P-code `BRANCHIND`가 관측된 지점 사이의 연속 구간을 후보로 만들었다. 시작·끝 PC를 검색 상수로 주지 않는다. 간접 분기는 VM 핸들러 외에도 존재하므로, 후보는 저장된 전체 네이티브 전이의 **경로 모양, guard, 진입 상태, 읽기 주소·값, 순서 있는 쓰기, 출력 상태, 다음 주소**를 모두 통과해야 승인된다.

| 전체 추적 | 후보 | 승인된 구간 | 결과 |
|---|---:|---:|---|
| Python 42 | 15 | 116명령 1개 | 읽기 31·쓰기 12개와 상태·다음 주소 일치 |
| JavaScript 42 | 120 | 23명령 1개 | 읽기 8개와 상태·다음 주소 일치 |
| 새 Python 43 | 15 | 116명령 1개 | 저장된 전이 적용, 대상 P-code 재생 0회 |
| 새 JavaScript 43 | 120 | 23명령 1개 | 저장된 전이 적용, 대상 P-code 재생 0회 |
| Python 252 | 15 | 없음 | 같은 진입을 가진 146명령의 다른 할당 경로이므로 `unknown` |

잘못된 분배 경계, 읽기 주소, Python 쓰기, 후속 주소를 바꾼 경우는 승인되지 않았다. [경계 결과](dispatch_interval_discovery_result.json)에 각 후보의 인덱스와 검사 결과를 저장했다. [통합 실행기](run_integrated_pipeline.py)의 Python·JavaScript 숫자 구간도 이제 고정 시작·끝 PC 대신 이 후보 생성과 전체 전이 판정으로 선택한다.

이는 **이미 동결한 요약을 전체 추적에서 자동으로 찾아 적용하는 기능**이다. `252`는 새 후보에서 저장된 경로 모양과 일치하는 구간이 없어 `unknown`인 회귀 사례다. 모르는 핸들러를 정적 바이너리에서 혼자 발견하거나 모든 분기 출구를 열거한 결과는 아니다. Lua의 이전 23명령 요약은 전체 핸들러가 아닌 중간 절단점이므로 이 두 간접 분배 경계 규칙으로 승인하지 않았다.

## 재현

```bash
cd experiments/interpreter-expression
../vm-transition-testbed/.venv/bin/python discover_dispatch_intervals.py
../vm-transition-testbed/.venv/bin/python audit_observed_dependencies.py
../vm-transition-testbed/.venv/bin/python run_integrated_pipeline.py
../vm-transition-testbed/.venv/bin/python analyze_dependency_slice.py
```

새 `43`과 범위 밖 `252` 추적은 기존 `trace_cross_full_flow.py --watch-bridge --through-return`을 고정된 CPython 3.13.5·Node 24.19.0에서 실행해 수집했다. 평가 스크립트는 출력 확인에만 쓰며 경계 후보를 고르는 입력이 아니다. 모든 새 코드·추적·결과는 `R4interpreter`에만 저장한다.

## 다음 연구 질문

JavaScript 전체 호출자의 `rep`·원자 명령·AVX-512 흐름을 지원하려면 명령 내부 반복의 메모리 접근 순서와 마스크 값을 명시해야 한다. 현재 추적의 접근 모드가 0인 6곳도 다시 수집하거나 확인된 명령 의미로 보강해야 한다. 그전까지 전체 호출자 슬라이스를 실행 가능한 축약 프로그램이나 임의 입력에 대한 완전한 의존성 증명으로 사용하면 안 된다. 다음 확장은 요약이 없는 후보에서 VM 상태·효과 경계를 제안하고, 개별 후보의 read/write alias와 guard를 증명하는 것이다.
