# JavaScript 문자열 길이별 전이와 공통 문자 복사

> 이 문서의 다섯 자리 전체 전이 `unknown`은 당시 고정 경로 요약의 결과다. 후속 [루프 합성 실험](JS_STRING_LOOP_COMPOSITION_RESULT.md)에서 반복 구간을 조합해 다섯 자리부터 열한 자리까지의 전체 전이를 추가 확인했다.

## 질문

직전 실험은 `"37" + 5`의 전체 네이티브 전이를 요약하고 `"38"`에 재사용했지만, 세 자리 `"251"`은 다른 경로여서 `unknown`이었다. 이번에는 길이가 바뀌어도 재사용되는 부분과 길이마다 달라지는 전체 상태 전이를 분리해 확인했다. 고정 Node 24.19.0 `--jitless` 실행기와 같은 JavaScript fixture를 사용했다.

## 전체 네이티브 전이

| 입력 문자열 길이 | 요약 소스 | 네이티브 명령 | P-code 연산 | 순서 있는 쓰기 | 별도 적용 입력 |
|---:|---:|---:|---:|---:|---|
| 1 | `"9"` | 219 | 1011 | 29 | `"0"`, `"8"` |
| 2 | `"37"` (이전 요약) | 230 | 1055 | 30 | `"10"`, `"38"`, `"99"` |
| 3 | `"251"` | 232 | 1064 | 31 | `"252"`, `"999"` |
| 4 | `"1000"` | 237 | 1095 | 32 | `"1001"`, `"1009"` |

한·세·네 자리 요약은 [길이별 전체 전이 JSON](js_string_length_paths_summary.json)에, 두 자리 요약은 [기존 JSON](js_string_add_full_handler_summary.json)에 있다. 모두 16개 범용 레지스터, 모델링한 플래그 5개, 읽기 주소, 쓰기 순서·주소·값, 다음 `Return` 핸들러 경계를 저장한다. 입력 계약은 실제 문자열 객체의 길이·ASCII 숫자 바이트와 `AddSmi` 즉값 5를 확인한다. 같은 실행 파일의 다른 입력에 적용할 때 대상 P-code는 다시 재생하지 않았다.

[공통 적용 결과](common_three_engine_application_result.json)는 기존 Lua·Python·JavaScript 사례를 포함해 **23건 중 21건 일치, 2건 `unknown`**이다. 두 `unknown`은 기존 숫자 입력 252와 새 다섯 자리 문자열 `"10000"`이다. 다섯 자리 문자열도 실제로 `"100005"`를 출력하지만, 239개 명령의 다른 전체 경로에 대한 전이 요약은 만들지 않았다. 피연산자·출력 바이트 등을 변조한 부정 입력 15개는 모두 거부했다. 이 수치는 고정 바이너리와 관측 경로에 대한 차등 검증이며, 모든 문자열의 경로 완전성을 뜻하지 않는다.

## 길이를 넘어 공통인 부분

원본 문자열의 문자 하나를 읽고 결과 객체의 같은 위치에 쓰는 **두 네이티브 명령**을 P-code로 다시 계산했다. 두 글자씩 복사하는 `0x1ab4145`, `0x1ab414f` 쓰기가 네·다섯 자리에서 반복되고, 홀수 글자의 마지막 복사는 `0x1ab4167`을 사용한다. 각 경로의 끝에서는 `0x1ab41f1`이 문자 `'5'`를 쓴다.

[문자 복사 증명 결과](js_string_copy_family_result.json)는 한 자리부터 다섯 자리까지 소스 경로 5개에서 **문자 복사 15곳과 끝 문자 5곳**을 검사한다. 한 문자만 기호 바이트로 바꾸고 그 위치의 진입 레지스터와 다른 메모리는 관측값으로 고정했다. 쓰는 바이트·주소가 예상과 다르거나 해당 구간의 guard가 배제된다는 반례 질의는 모두 `unsat`였다. 겹치는 모든 네이티브 쓰기를 순서대로 합쳐 최종 객체 바이트를 재구성했고, 14개 관측 입력의 실제 문자열 출력과 맞았다.

두 글자 복사 구간은 별도로 한 번 더 일반화했다. `0x1ab4140 → 0x1ab4145 → 0x1ab4149 → 0x1ab414f`의 네 명령에 원본 주소 `SRC`, 목적지 주소 `DST`, 위치 `OFFSET`, 초기 메모리를 모두 기호값으로 넣었다. 첫 출력 쓰기가 아직 읽지 않은 두 번째 원본 바이트를 덮지 않는 조건(`DST+OFFSET ≠ SRC+OFFSET+1`)에서, 두 읽기와 두 쓰기의 주소·값이 예상과 다르다는 반례는 `unsat`였다. 출력 두 바이트 밖의 메모리가 변하거나 세 주소 레지스터가 바뀐다는 반례도 `unsat`였다. 조건을 빼고 첫 쓰기가 두 번째 원본을 덮게 만들면 잘못 복사되는 `sat` 반례가 실제로 나온다. 이 **하나의 P-code 복사 규칙과 같은 명령 바이트**가 길이 2~5의 관측 경로에서 6번 나타난다.

따라서 다섯 자리에서는 **문자 복사라는 값 규칙은 확인되지만 전체 상태·효과 전이는 `unknown`**이다. 기호 복사 규칙은 한 네이티브 블록에 대한 것이며, 범용 길이의 루프 불변식이나 임의 alias에서 실행 전체가 그 블록에 도달한다는 증명은 아니다. 길이별 할당·루프 분기·레지스터·메모리 효과를 하나의 반복 가능한 요약으로 합치려면 루프 진입/종료 조건과 효과 합성, 객체 정체성·alias 검증이 더 필요하다. 현재 입력 계약은 ASCII 십진 숫자 문자열과 오른쪽 Smi 5에 한정되며, 다른 문자·타입·JIT 버전은 다루지 않는다. `daasdmlkas`는 읽기 전용 참고 대상으로 유지했다.

## 다음 실험

1. 반복되는 두 문자 복사 구간을 매개변수화한 P-code 루프 전이로 만들고, 길이 5 이상에서 **전체** 상태·효과를 예측할 수 있는지 확인한다.
2. 할당 객체와 후속 호출자의 관찰 위치를 연결해, 결과에 영향을 주지 않는 네이티브 효과를 alias·생존성 근거로 제거한다.
3. BigInt의 부분 추적을 실제 `Throw`/catch 경계까지 연장하고 예외 효과를 공통 형식에 추가한다.
