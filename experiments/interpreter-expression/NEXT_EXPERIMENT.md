# 후속 실험: 실행기 입력에서 VM 피연산자까지

첫 진입의 명령 주소와 한 덧셈 연산에 대한 최소 검증은 [첫 추적 결과](FIRST_TRACE_RESULT.md)에 기록했다. 아래 입력 출처·선택 경로 계산식·별도 입력 범위 확인 결과는 [1~3단계 결과](INPUT_PROVENANCE_RESULT.md)에 기록했다.

바이트코드 인덱스와 네이티브 처리 구간의 첫 대응은 [두 입력의 결과](BYTECODE_HANDLER_RESULT.md)에서 확인했다. 다음 우선순위는 다른 바이트코드에서 같은 분석 절차가 재사용되는지 확인하는 것이다.

## 목적

정적 `run_lua_chunk` 슬라이스의 미해결 의존과 `luaV_execute`의 다수 JOIN 때문에 아직 결과식을 만들지 못했다. 첫 경로 기록 실험은 **한 번 실행된 네이티브 연산을 Ghidra P-code 연산에 대응**시키는 것을 목표로 한다. Lua opcode나 원본 소스는 분석 입력으로 사용하지 않는다.

## 순서

1. 별도 자식 프로세스에 `ptrace` 단일 단계 추적이 가능한지 작은 ELF로 확인한다. 기록 한 줄은 `(ELF SHA-256, 실행 순번, 명령 주소, 레지스터 전후값, 메모리 접근 주소·폭·값, 분기 후 주소)`를 가진다. 메모리 접근값을 신뢰할 수 없으면 이 단계에서 멈추고 계측 방식을 바꾼다.
2. 같은 추적기를 `lua_interpreter_fixture`의 `luaV_execute` 구간에 적용한다. 바이트코드는 `lua_chunk.luac`로 고정하고 입력 `0`, `1`, `9`를 각각 실행한다. 실행 순번으로 같은 명령의 반복 실행을 구분한다. 초기에는 최대 실행 명령 수와 시간 제한을 둔다.
3. 각 실행 명령 주소를 보관된 Ghidra Bundle의 명령/P-code 묶음에 대응한다. 최소 한 번의 Lua 정수 덧셈 경로에서 실제 레지스터·메모리 읽기/쓰기가 P-code 재생 결과와 맞는지 확인한다.
4. 해당 경로의 입력값만 심볼로 바꿔 결과식과 guard를 만든다. 계측에 사용하지 않은 입력으로 같은 경로의 출력이 일치하는지 확인한다. 다른 경로, 불명확한 메모리 별칭·호출 효과는 `unknown(reason)`으로 보고한다.

## 첫 통과 조건

- 작은 ELF에서 P-code 연산 순서와 실행값이 맞는다.
- Lua VM 안에서 실제 실행된 명령 주소·반복 순서·분기 결과를 재현 가능하게 기록한다.
- 선택한 Lua 경로의 결과식은 입력을 바꾸어도 같은 guard 안에서 실행값과 일치한다.
- 기록되지 않은 경로에 대한 일반식을 주장하지 않는다.

`ptrace`가 이 환경에서 막히거나 한 입력당 추적 비용이 과하면 그 원인과 규모를 기록하고 DBI 기반 추적으로 바꾼다. 이때도 기록 형식과 판정 기준은 유지한다.
