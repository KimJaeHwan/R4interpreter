# 전체 로직 복원 1·2단계와 첫 대체 분기

이번 단계는 [공통 프로그램 표현](COMMON_PROGRAM_REPRESENTATION_RESULT.md)과 [제어 흐름 작업 목록](COMMON_CONTROL_WORKLIST_RESULT.md)을 연결했다. 바이트코드에서 네이티브 실행으로 넘어가는 증거를 보강하고, 결과값만 따라가는 역방향 slice가 무엇을 빠뜨리는지 같은 방식으로 세 엔진에서 측정했다. 전체 프로그램을 디컴파일하거나 무관한 네이티브 분기를 삭제한 결과는 아니다.

## 1. 바이트코드와 경계 연결

새 [Lua 분배 지도](lua_branch_dispatch_map_v1.json)는 `lua_branch_call.luac`를 실행한 입력 `0`, `9`의 기존 원시 추적을 다시 읽는다. 고정 Lua ELF의 네이티브 명령에서 `LOAD` → 하위 7비트 마스크 → `BRANCHIND`를 P-code로 확인했다. 각 실행에서 캡처된 분배 6회 모두에 대해 바이트코드의 4바이트 값, 파일 위치, 점프 테이블 읽기와 실제 진입 주소가 일치했다. Lua opcode 이름이나 원본 스크립트의 문법을 대응 근거로 쓰지 않았다.

| 입력 | 분기 후 실행된 바이트코드 파일 위치 | 호출된 덧셈 구간의 바이트코드 위치·수치 opcode·네이티브 진입 |
| --- | --- | --- |
| `0` | `47, 51, 59, 63, 67` | `111` · `21` · `0x4164b8` |
| `9` | `47, 51, 75, 79, 83` | `111` · `21` · `0x4164b8` |

두 입력은 분기 뒤 다른 바이트코드 위치를 실행하지만 같은 호출된 구간에 도착한다. 오프셋 `111`의 분배 발생은 각 입력의 [연속 VM 값 구간](boundary_relevance_map_v1.json) 안에 있다. 이것은 해당 추적의 **값·opcode 인덱스 레지스터·점프 테이블 읽기·진입점 일치**이며, 정적 세 명령만으로 테이블 주소 계산 전체를 증명한 것은 아니다. 지도에서 사용하는 `index_from_min_observed_address`는 함수 시작부터 센 번호가 아니라 관측한 최소 주소부터 센 번호다. 실행되지 않은 바이트코드의 의미나 다른 출구도 밝히지 않았다. Lua의 별도 `plus11` 로컬 구간은 **다른 바이트코드 파일**이므로 주소 `0x4164b8`가 같아도 위 오프셋 `111`을 그 구간에 붙이지 않았다.

공통 [경계 지도](boundary_relevance_map_v1.json)는 경계 17개를 다음처럼 구분한다.

| 경계 종류 | 수 | 승인 근거와 한계 |
| --- | ---: | --- |
| Python 관측 간접 분배 사이 구간 | 8 | 네 정확한 입력에서 숫자 구간과 다음 분배 구간의 시작·끝을 기존 전체 전이 증명서에 대조. 선택된 바이트코드의 **개별 offset은 아직 없음** |
| Lua·JavaScript 로컬 값 절단점 | 2 | 저장된 구간 전이를 재사용했으나 해당 소스 추적의 바이트코드 분배 쌍이라는 주장은 없음 |
| Lua 분기·호출의 연속 VM 값 구간 | 7 | 연속 네이티브 실행 구간. 입력 `0`·`9`에는 같은 추적의 바이트코드 분배 발생을 추가 연결했고, 나머지 다섯 입력의 fetch 위치는 아직 직접 대응하지 않음 |

JavaScript의 다른 전체 추적에서는 같은 길이의 숫자 구간을 분배 쌍 사이에서 찾았지만, 로컬 구간의 픽스처와 같은 바이트코드라고 증명하지 않았다. `BRANCHIND` 사이에 끼어 있다는 사실만으로 하나의 VM 명령 또는 모든 입력에 공통인 handler 경계라고 판정하지 않는다.

## 2. 결과 관련성의 안전한 첫 분류

Python 입력 `252`의 숫자 구간 146명령, Lua 입력 `0`의 연속 VM 구간 237명령, JavaScript 숫자 로컬 구간 23명령에서 동일한 P-code 역방향 slice 구현을 사용했다. 실제 실행된 명령 내부 P-code 경로만 선택하고, 세 가지 sink 범위를 비교했다.

| 선택된 P-code 연산 | 결과값만 | 결과값 + 관측 쓰기 주소의 바이트 | 앞의 항목 + 주소와 모든 관측 제어 의무 |
| --- | ---: | ---: | ---: |
| Python | 6 | 103 | 311 |
| Lua | 27 | 146 | 515 |
| JavaScript | 8 | 8 | 47 |

마지막 열은 **모든 관측 제어 연산을 보존하도록 요청한 결과**다. 그 숫자가 모두 반환값에 영향을 준다는 증명은 아니다. 중간 열도 관측된 쓰기 주소를 sink로 추가한 구조적 의존성 결과이며, 쓰기 간 별칭이나 객체 수명의 안전성을 증명하지 않는다. 선택한 세 구간에서는 명령 내부 P-code 미지원 항목이 0건이었다. 이는 경로 밖의 분기나 메모리 효과까지 닫혔다는 뜻이 아니다.

기존 [작업 목록](common_control_worklist_v1.json)의 **720개 분기·호출 발생을 모두 보존**했다. 위 세 slice 범위에 든 분기 44개는 도달성 의무, 호출 3개는 정상 복귀·예외 의무로 유지했다. 범위 밖의 673개는 관련성 미해결이다. 이번 자료로 안전하게 삭제할 수 있다고 판정한 분기는 **0개**다. 실제 Python 추적의 `cmov`에서 실행되지 않은 정의·변경된 플래그·잘못된 후속 주소를 승인하지 않는 네 사례도 다시 확인했다.

## 3단계의 첫 대체 분기

두 Lua 입력은 바이트코드 파일 오프셋 `51`의 같은 수치 opcode `61`에서 네이티브 `0x415ee0`으로 들어간다. 그 뒤 처음 20개 네이티브 명령의 PC·후속 주소가 같고, 다음 `0x415f30`에서 처음 다른 방향을 택한다.

| 입력 | `0x415f30`의 실제 후속 주소 | 다음으로 캡처된 바이트코드 파일 위치 | 기존 전체 VM 구간의 증명된 경로 조건 |
| --- | --- | ---: | --- |
| `0` | `0x415d51` | `59` | `X == 0` |
| `9` | `0x415f36` | `75` | `X != 0` |

두 네이티브 실행은 handler 진입부터 다음 fetch까지 각각 연속 기록이며, 두 주소는 해당 조건 분기 명령의 합법적인 후속 주소다. 발생 ID `lua_branch_x0:branch:32`와 `lua_branch_x9:branch:32`도 기존 작업 목록에 연결했다. 표의 경로 조건은 **전체 VM 구간의 조건**이다. `0x415f30` 한 명령의 조건식만 독립적으로 `X == 0`이라고 증명한 것은 아니며, 다음으로 캡처된 fetch가 바로 다음 바이트코드 명령이라는 뜻도 아니다. 이는 3단계 전체를 닫은 결과가 아니라 첫 대체 경로의 구체적 출발점이다.

## 재현과 다음 단계

```bash
cd /workspace/R4interpreter
experiments/vm-transition-testbed/.venv/bin/python experiments/interpreter-expression/map_lua_branch_dispatch.py
experiments/vm-transition-testbed/.venv/bin/python experiments/interpreter-expression/build_boundary_relevance_map.py
```

첫 스크립트는 Lua 분배 기록을 원시 추적·파일·네이티브 바이트에서 다시 만들고 다섯 가지 증거 변조를 거부한다. 관측 주소가 역순인 사례에서도 파일 위치를 다시 계산한다. 두 번째 스크립트는 상위 프로그램 IL·제어 작업 목록·Lua 분배 지도를 **각 원천 자료에서 재생성해 대조**한 다음 경계, slice, 720개 의무를 만들고 지도 변조 일곱 가지 및 상위 입력 변조 세 가지를 거부한다. JavaScript의 다른 추적에서 승인된 분배 쌍도 다시 판정한다. 이 변조 사례들은 저장된 증거와 범위 표시의 무결성 검사다. `cmov` 네 사례는 실제 명령 내부 실행 선택 검사다.

**3단계의 다음 작업**은 이 첫 분기의 조건식을 해당 네이티브 명령까지 독립적으로 확인하고, 다른 분기·호출의 반대쪽 경로를 수집하며 정상·예외 후속 상태를 따로 모델링하는 일이다. Python·JavaScript의 선택된 숫자 구간에도 실제 바이트코드 cursor를 같은 추적에서 연결해야 한다. 그다음에야 각 바이트코드 전이를 VM 상태 변화로 묶고, 4단계의 일반 allocator 효과와 5단계의 전체 IL 출력으로 넘어갈 수 있다. 현재 `whole_program_complete=false`다.
