# 인터프리터 계산식 확장 실험 계획

상태: 계획, 1~3단계 최소 검증, Lua 정적 기준선 및 첫 실행 경로 관측 완료. 기준 코드: `main`의 `3a274f93d455d3caaebf72365e64820770341787`. 이 문서는 실험의 입력, 비교 대상, 판정 기준과 현재까지의 결과를 기록한다.

## 1. 목표와 범위

고정된 프로그램을 실행하는 인터프리터 바이너리에서, 원본 스크립트나 가상 opcode의 의미표 없이 **입력 조건과 관찰 가능한 출력의 계산식**을 얻는다. 첫 실제 언어는 JIT을 사용하지 않는 Lua 5.4다. VMP와 난독화 해제는 이번 실험의 범위 밖이다.

분석기가 받을 수 있는 것은 네이티브 바이너리, 실행할 프로그램의 바이트, 입력, Ghidra Low P-code Bundle, 네이티브 실행 관측이다. 프로그램 소스와 Lua opcode 정의는 평가용 정답을 만드는 쪽에만 둔다. 바이트코드가 고정된 실험에서는 그 바이트를 구체값으로 취급할 수 있지만, opcode 번호에 미리 의미를 부여하지 않는다.

첫 결과의 형식은 다음과 같다.

```text
sink: 반환값 또는 외부 출력
guard: 이 식이 적용되는 입력 조건
expression: 입력에 대한 비트 폭이 명시된 값 식
evidence: 사용한 P-code 연산과, 동적 분석이라면 실행 사건
assumptions/debts: 모델에 기댄 부분과 해결하지 못한 부분
scope: 관측 경로 / 검증된 경로 / 검증된 유한 영역
```

예를 들어 `guard: ult64(x, 10)`, `expression: bvadd64(x, 1)`은 무부호 조건과 64비트 래핑 의미를 함께 전달한다. 한 번의 실행에서 출력값 `8`을 보았다는 사실만으로 이 식을 보고하지 않는다.

## 2. 기존 코드에서 사용할 것과 새로 필요한 것

현재 경로는 [`GhidraV2BundleExport.java`](https://github.com/KimJaeHwan/daasdmlkas/blob/3a274f93d455d3caaebf72365e64820770341787/ghidra/GhidraV2BundleExport.java)의 Low P-code Bundle에서 출발해 [`NormalizedFunction`](https://github.com/KimJaeHwan/daasdmlkas/blob/3a274f93d455d3caaebf72365e64820770341787/src/tdo_v2/normalize.py)의 바이트 단위 SSA 및 의존 그래프, [`FunctionSummary`](https://github.com/KimJaeHwan/daasdmlkas/blob/3a274f93d455d3caaebf72365e64820770341787/src/tdo_v2/function_summary.py), [`BackwardSliceQuery`](https://github.com/KimJaeHwan/daasdmlkas/blob/3a274f93d455d3caaebf72365e64820770341787/src/tdo_v2/query.py)로 이어진다. 메모리 별칭, 호출 효과, 제어 의존성, 미해결 부채와 이름 붙은 가정은 이 경로에서 재사용한다.

`FunctionSummary.SummaryRun`의 `COMPUTED`는 입구 바이트 **집합에 대한 의존**을 나타낸다. 일반 산술식과 그 식이 성립하는 경로 조건은 나타내지 않는다. [`configured_function_integer_values`](https://github.com/KimJaeHwan/daasdmlkas/blob/3a274f93d455d3caaebf72365e64820770341787/src/tdo_v2/integration/configured_function_integer_values.py)의 작은 유한 값 집합은 상수 전파에 유용하지만 입력에 대한 일반적인 식은 아니다. [`tests/intra/pcode_interpreter.py`](https://github.com/KimJaeHwan/daasdmlkas/blob/3a274f93d455d3caaebf72365e64820770341787/tests/intra/pcode_interpreter.py)는 P-code 테스트 오라클이며 실제 Lua 실행 추적기가 아니다.

처음에는 기존 `SummaryRun`, `RootSlice`, 완전성 판정을 바꾸지 않는다. 별도의 `ExpressionProjection` 결과를 만들어 기존 노드·정의 ID·P-code 연산 키에 연결한다. **출처 추적의 완전성**과 **계산식의 정확성/적용 범위**를 별도로 보고한다. 미해결 읽기, 호출, 별칭, 지원하지 않는 연산을 임의의 독립 변수로 바꿔 완전한 식으로 주장하지 않는다.

## 3. 별도로 비교할 계산식 생성 방향

| 방향 | 방법 | 유리한 점 | 주된 한계 | 먼저 확인할 실험 |
|---|---|---|---|---|
| A. 정적 슬라이스에서 식 투영 | sink의 backward slice와 원본 P-code 피연산자 순서·폭, SSA 읽기 조각을 결합해 비트벡터 식으로 올린다 | 기존 그래프와 함수 요약을 가장 직접적으로 재사용한다 | 인터프리터 디스패처의 여러 경로·반복이 합쳐져 식이 커지거나 불명확해질 수 있다 | 먼저 JOIN 없는 직선 코드, 이후 부분 레지스터 쓰기와 분기를 각각 검증 |
| B. 실행 추적에 맞춘 P-code 재생 | 실행한 명령의 주소·순서·메모리 접근을 Bundle의 P-code와 대응시키고, 입력만 심볼로 둔 채 실행 경로를 재생한다 | 실제 Lua 경로와 메모리 주소를 구별하기 쉽다 | 관측한 경로 밖에는 결론이 없고 별도 추적 어댑터가 필요하다 | 같은 바이너리를 두 입력으로 실행해 서로 다른 분기 식과 guard를 얻는지 확인 |
| C. 정적 슬라이스 + 추적 + 제약식 | A로 관련 연산을 제한하고 B로 경로와 별칭을 구체화한 뒤, SMT로 guard와 식을 검사·병합한다 | 제한된 영역에 대한 검증 가능한 식을 목표로 할 수 있다 | 호출, 반복, 객체 의미의 모델링 비용이 가장 크다 | A/B 결과가 일치하는 작은 분기 프로그램에서 경로 병합 |

기존의 유한 값 전파·포인터 경로 추론을 확장하는 방법은 **보조 실험**으로 둔다. 주소·인덱스 범위를 좁히고 간접 호출을 해소하는 데 기여하는지 측정하되, 유한 값 집합만으로 `f(x)`를 복원했다고 평가하지 않는다.

권장 순서는 **A로 P-code 값 의미와 현재 SSA의 적합성을 확인 → B로 Lua 실행을 특화 → C로 적용 범위를 넓히기**다. A에서 디스패처 때문에 슬라이스가 지나치게 커지면 A 단독 확장을 중단하고 B에 필요한 공통 식 평가기만 유지한다.

## 4. 공통 표현과 정확성 규칙

- 연산은 폭을 가진 비트벡터로 표현한다. 부호 비교, 무부호 비교, 확장, 절단, 시프트, 오버플로, 메모리 바이트 순서를 구별한다.
- 레지스터의 일부 바이트에 쓴 결과는 전체 값의 해당 비트만 교체한다. 메모리는 객체·주소·폭을 보존한다. 주소 의존성도 데이터 의존성과 함께 추적한다.
- 분기 결과의 관측과 정적 제어 의존성은 별개다. guard에는 실제 조건식과 선택한 후속 경로가 들어가야 한다. 합류의 `ite`는 양쪽 경로가 모델에 포함될 때만 만든다.
- 현재 `MemoryJoinInput`에는 이전 블록별 정의의 대응이 없고 `ControlDependence`에는 참·거짓 방향이 없다. 분기 식에는 원본 CFG와 P-code 조건을 이용한 대응 복원이 필요하다. 분기 입력을 찾는 질의는 `include_control=True`를 사용하되, 이것만으로 guard가 만들어졌다고 간주하지 않는다.
- 정적 그래프의 연산 키는 반복 실행마다 같다. 동적 사건에는 `(바이너리 식별자, 명령 주소, 실행 순번, P-code 연산 순번)` 같은 별도 식별자가 필요하다.
- 외부 호출과 함수 간 식은 증명된 요약 또는 명시한 모델을 통해서만 합성한다. 불투명 호출은 부채로 남긴다. 루프는 첫 단계에서 반복 상한을 명시하고, 그 범위를 넘는 입력에는 식을 적용하지 않는다.
- 결과 등급을 `observed`(실행 표본만 일치), `path-checked`(명시된 경로 조건과 모델 아래에서 SMT 반례 없음), `finite-domain-checked`(명시된 유한 입력 영역 전수 비교)로 구분한다. 새 입력 몇 개를 맞힌 사실은 경로 전체의 증명이 아니다.

## 5. 실험 대상과 입력

### 단계 N: 네이티브 기준선

Linux x86-64 ELF에서 작은 C 함수들을 컴파일한다. 분석기에는 실행 파일과 입출력 경계만 주고, C 소스는 오라클에만 준다. 처음에는 호출 없는 함수, 다음에는 직접 호출을 포함한다. `-O0`과 `-O2`를 나누어 본다.

| 사례 | 확인할 성질 |
|---|---|
| `x + 7`, `3*x` | 비트 폭, 래핑, 입력 의존 식 |
| `(x ^ 0x55) & 0xff` | 비트 연산과 부분 바이트 |
| `x < 10 ? x + 1 : 2*x` | 분기 guard와 두 경로 |
| 겹치는 폭의 저장·읽기 | 메모리 SSA, 엔디언, 별칭 |
| 짧은 제한 반복 및 직접 호출 | 반복 상한과 식 요약의 크기 |
| 불투명 호출·미해결 간접 분기 | 완전한 식 대신 부채 보고 |

작은 입력 폭은 전수 비교하고, 64비트 사례는 경계값·미사용 입력과 적용 가능한 SMT 등가성 검사를 조합한다. C의 미정의 동작 때문에 오라클이 흔들리지 않도록 처음에는 명시적인 무부호 연산을 쓴다.

### 단계 L: 첫 실제 언어 — Lua 5.4

Lua를 정적으로 연결한 작은 C 실행기를 사용한다. 실행기는 정수 입력을 Lua에 전달하고 고정된 Lua chunk의 정수 결과를 반환한다. chunk의 소스는 평가자만 보관하며 분석기는 chunk 바이트와 네이티브 바이너리만 받는다. 첫 프로그램은 `x + 7`, 두 경로의 조건문, 상한이 작은 누산 루프다. 처음에는 정수, 단일 스레드, 결정적 입출력으로 제한한다.

Ghidra Bundle에서 실행기의 입출력 경계부터 Lua 내부까지의 정적 슬라이스를 먼저 얻고, **도달한 입력·부채·노드 수·처리 시간**을 기록한다. 이 결과가 지나치게 넓으면 동적 실행 기록으로 해당 실행에서 지나간 명령과 메모리 접근을 제한한다. 네이티브 추적 도구는 명령 주소, 분기 결과, 메모리 주소·값을 재현 가능하게 수집할 수 있는지 작은 ELF에서 확인한 뒤 선택한다.

Lua와 네이티브 기준선은 정수 범위 및 오류 동작이 같은 입력에서 비교한다. 초기 실험에는 문자열, table, closure, 예외, GC 압박, JIT을 넣지 않는다. 이 기능들은 기본 정수 실험의 결과와 비용을 확인한 뒤 별도 사례로 추가한다.

## 6. 판정 지표와 중단 기준

각 방향을 같은 사례와 같은 입력 분할에서 비교한다. 대조군은 현재 엔진의 출처·부채 결과, 식을 만들지 않는 실행값 추적, 슬라이스 없이 P-code를 재생하는 방법으로 둔다. 이를 통해 식 정확도뿐 아니라 기존 슬라이스가 연산량과 결과 크기를 얼마나 줄였는지 확인한다. C 단계에서는 정적 슬라이스 제한, 동적 경로 제한, 별칭 구체화를 각각 끈 비교도 기록한다.

1. **식의 정확성:** 보고한 guard 안의 새 입력에서 값과 관찰 가능한 효과가 일치하는가? 검증 방식과 범위를 결과마다 기록한다.
2. **적용 범위:** 관측·검증·미해결 경로 및 입력 영역이 각각 얼마인가? 미관측 경로를 자동으로 성공 처리하지 않는다.
3. **재사용성:** Lua 전용 opcode 규칙이나 소스 정보 없이 같은 P-code 식 평가기를 네이티브와 Lua에 적용하는가? 실행기별 경계 설정·모델·수작업 시간을 따로 센다.
4. **비용:** Bundle 생성, 슬라이스, 추적, 식 생성, SMT 확인의 시간·메모리·결과 식 크기를 따로 기록한다.
5. **기존 엔진 영향:** 새 계층을 켰을 때 출처·부채·이름 붙은 가정이 사라지거나 기존 완전성 결과가 무근거로 강화되지 않는가?

한 사례에서 식을 증명할 수 없으면 `unknown(reason)`과 관련 P-code/실행 증거를 남긴다. 필수 지원 사례와 의도적인 미지원 사례를 분리해 성공 건수와 unknown 건수를 모두 보고한다. Lua에서 정적 슬라이스가 대부분의 VM 핸들러를 포함하거나 간접 분기가 미해결이면 이를 A의 측정 결과로 기록하고 B 실험으로 넘어간다. B가 새 입력을 설명하지 못하면 경로 요약으로 주장하지 않고 관측 결과로만 남긴다.

## 7. 작업 순서와 산출물

| 순서 | 산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 0 | 입출력 경계와 결과 스키마, 정답·학습·미사용 입력 분리 | 식, guard, 부채, 적용 범위를 구분해 저장 |
| 1 | 합성 P-code의 기존 backward slice 및 SSA 읽기 조각 확인 | 입력에서 결과 정의까지 피연산자 순서와 의존을 연결 |
| 2 | A의 최소 비트벡터 식 평가기와 독립 P-code 오라클 비교 | `x+7`, `7-x`, 두 연산 연결 모두 256개 입력 일치; 미지원 연산 1건 unknown; 잘못된 상수·피연산자 순서·폭 변형 검출 |
| 3 | 실제 작은 ELF의 Ghidra Bundle과 같은 식 투영 | 합성 관측에서 쓴 가정 없이 계산식과 오라클 일치 |
| 4 | 부분 레지스터와 한 번의 분기/JOIN을 별도 검증 | 폭·이전 블록별 정의·분기 방향 근거를 보존 |
| 5 | 작은 ELF의 실행 사건 ↔ P-code 연산 대응 검증 | 같은 명령의 반복 실행을 구분하고 읽기·쓰기 값을 대조 |
| 6 | B의 경로별 식과 Lua 정수 사례 | 미사용 입력에서 guard 안의 결과 일치, 경로 밖은 미해결 표시 |
| 7 | C의 조건부 식 병합 여부 결정 | 정확성·적용 범위 증가가 비용과 새 가정을 정당화 |

기존 `tests/intra/pcode_interpreter.py`는 P-code 연산값과 의존성의 오라클로 활용한다. 새 검증에는 오류를 주입한 식(잘못된 부호 비교, 바이트 순서, 분기 방향, 호출 효과)이 반드시 잡히는 사례를 포함한다. Lua 실험에서는 실행 기록에 사용하지 않은 입력으로 결과를 비교하고, 성공·미해결·실패를 구분해 보고한다. 각 실행의 바이너리·Bundle 해시, Ghidra 버전, Lua 버전, 컴파일 옵션, 입력 분할, 적용한 모델과 가정을 결과와 함께 보관한다.

## 8. 첫 검수·실험 기록

Astra 검수에서 다음 두 제한이 확인되었다. 현재 SSA JOIN에는 이전 블록별 정의 대응이 없고 제어 의존성에는 분기 방향이 없다. 또한 슬라이스 그래프의 의존 집합만으로는 `a-b`와 `b-a`를 구분할 수 없으므로 원본 P-code의 입력 순서와 SSA 읽기 조각이 모두 필요하다.

첫 실험은 저장소 밖의 [`expression_probe.py`](expression_probe.py)에서 기존 합성 P-code 생성기·정규화기·BackwardSliceQuery를 읽기 전용으로 사용했다. [`결과`](expression_probe_result.json)는 8비트 `x+7`, `7-x`, 두 연산 연결 `x+7-3`에서 각각 독립 P-code 실행기와 256/256개 입력이 일치하고, 정답 식과의 SMT 부등식이 `unsat`임을 기록한다. 잘못된 상수·피연산자 순서·폭 변형은 불일치를 냈고, 지원하지 않는 XOR은 `unknown`으로 남았다. 이는 **합성 관측의 JOIN 없는 식을 현재 SSA 연결에서 투영할 수 있다는 근거**다.

다음으로 [`elf_expression_fixture.c`](elf_expression_fixture.c)를 `gcc -O2 -fno-pie -no-pie`로 컴파일했다. 실제 ELF의 `add7`은 `lea 0x7(%rdi),%rax; ret`이다. 공식 Ghidra 12.0.4 배포본과 Temurin JDK 21의 공개 SHA-256을 확인한 뒤, 저장소의 exporter로 [`Bundle`](artifacts/elf_bundle.tar.gz)을 생성했다. [`elf_expression_probe.py`](elf_expression_probe.py)는 Bundle을 admission·normalize하고 RAX의 8바이트 쓰기를 sink로 잡았다. 기존 SSA의 RDI entry 정의→`INT_ADD`→unique 임시값→`COPY`→RAX 정의를 이어 `x + 7` (64비트)을 만들었다. 슬라이스는 노드 5개, 입력 1개, 미해결 읽기 0개였다.

[`ELF 결과`](elf_expression_probe_result.json)에서 C fixture 사양과의 64비트 비트벡터 부등식은 SMT `unsat`였고, ELF를 직접 실행한 경계값 9개와 고정 시드 의사난수 128개가 투영식과 모두 일치했다. 일부러 `+8`로 바꾼 식은 137개 모두 불일치했다. **이 결과는 Ghidra Low P-code의 단순 직선 함수에 기존 SSA와 backward slice를 재사용할 수 있다는 근거**다. SysV AMD64의 RDI 입력·RAX 반환과 Ghidra의 해당 명령 모델을 전제로 한다. 64비트 전체에 대한 네이티브 실행 전수 검증과 분기/JOIN·호출에 대한 식 검증은 아직 없다.

## 9. Lua 5.4 첫 기준선 측정

네이티브 분기·부분 레지스터 사례보다 인터프리터 실험을 앞당겼다. Lua 5.4.8(`v5.4.8`, `6e22fedb74cf0c9b6656e9fce8b7331db847c605`)을 저장소 밖에 빌드하고 [`실행기`](lua_interpreter_fixture.c)가 디버그 정보를 제거한 [`바이트코드`](lua_chunk.luac)를 파일에서 읽도록 했다. 바이트코드를 만드는 [도구](lua_compile_chunk.c)와 [평가용 Lua 소스](lua_chunk_source.lua)는 결과 검증에만 사용한다. 실행기 ELF는 Lua 런타임을 정적으로 링크했고, `return x + 7`에 대해 경계값 7개와 고정 시드 의사난수 128개, 총 135개 입력이 평가용 사양과 일치했다. 이는 **실행기 확인**이며 분석기가 식을 복원한 결과는 아니다.

Ghidra 12.0.4로 `run_lua_chunk`와 참조 폐포를 [`Bundle`](artifacts/lua_bundle.tar.gz)로 추출했다. 318개 함수 관측 파일, 약 42MB다. 첫 함수 `run_lua_chunk`는 정규화되고 63개 네이티브 명령, 236개 P-code 연산을 갖는다. [`RAX 슬라이스 결과`](lua_root_probe_result.json)는 두 결과 쓰기에 각각 미해결 의존 4개와 6개를 보고했다. 따라서 현재 정적 식 투영은 `x + 7`을 완전한 식으로 보고할 수 없다.

Lua의 핵심 실행 함수 `luaV_execute`도 정규화된다. [`VM 규모`](lua_vm_probe_result.json)는 3,670개 네이티브 명령, 26,892개 P-code 연산, SSA JOIN 1,608개, 미해결 읽기 노드 442개를 기록한다. [`전체 정규화 기록`](lua_bundle_stats.json)은 앞의 60개 함수를 처리한 뒤 61번째 함수의 잘못된 관측 범위에서 중단했다. 별도 scope 진단은 318개 중 311개가 scope 구성 가능하고 7개가 `invalid_function_observation`임을 보였다. 이것은 전체 폐포 정적 분석의 현재 도구 경계다.

**다음 실험은 방향 B의 실행 경로 기록**이다. 같은 바이트코드에 서로 다른 정수 입력을 넣고 `luaV_execute`의 실제 명령 주소·분기 선택·메모리 읽기와 쓰기·실행 순서를 기록한다. 먼저 ELF의 작은 경로에서 native instruction과 Bundle P-code를 대응시키고, 그 다음 Lua 경로의 실행 인스턴스를 구분한다. 경로와 주소가 결정되지 않은 호출·JOIN은 부채로 남기며, 기록된 경로의 식을 미사용 입력으로 확인하기 전에는 `x+7`을 분석 결과라고 주장하지 않는다.

## 10. 첫 동적 경로 관측

[`첫 실행 추적 결과`](FIRST_TRACE_RESULT.md)를 별도로 보관했다. 입력 `9`에서 작은 ELF의 2개 명령과 Lua VM 첫 호출의 262개 명령을 기록했고, 전부 보관된 Bundle의 명령 주소에 대응했다. Lua의 조건 분기 19개 후속 주소도 Bundle과 일치했다. VM 내부 `0x417ce7`의 P-code `INT_ADD`에서는 메모리 값 `9`와 레지스터 값 `7`이 실행 후 `16`이 되고 다음 저장에 반영됐다. 메모리 피연산자를 일반적으로 디코딩하거나 입력의 전체 전달 경로를 얻은 것은 아니므로 결과는 한 경로의 `observed` 등급이다. 방향 B의 다음 관문은 입력에서 VM 스택까지의 주소·값 연결과 미사용 입력 검증이다.

## 11. 바이트코드→네이티브 코드 첫 대응

[`두 입력의 바이트코드 대응`](BYTECODE_HANDLER_RESULT.md)에서 실제 32비트 명령 읽기와 점프 테이블의 간접 분기를 묶었다. 바이트코드 인덱스 `0, 1, 2, 4`는 입력 `9`와 `0`에서 같은 네이티브 처리 구간으로 진입했다. 인덱스 `2`의 수치 opcode `21`이 실행한 구간에는 앞서 관측한 `INT_ADD`가 있다. 이는 바이트코드 명령 위치와 바이너리 경로의 **동적 대응**이며, 아직 Lua 언어 수준 의미나 일반 결과식의 복원은 아니다.

## 12. 입력 출처 결과와 처리 구간 요약 방향

[`입력 출처·선택 경로 계산식 결과`](INPUT_PROVENANCE_RESULT.md)에서 실행기 인자부터 VM 피연산자까지 실제 메모리 주소를 연결하고, 선택한 P-code 경로의 `(X+7) mod 2^64` 식을 얻었다. 별도 입력 6개와 정수 경계에서 같은 VM 경로 및 출력을 관측했다. 이 결과는 선택한 연산과 관측 경로의 검증이며, 생략한 중간 명령·메모리 효과까지 증명하지 않는다.

Astra와 검토한 [후속 설계](VM_HANDLER_SUMMARY_DESIGN.md)는 바이트코드 분배 경계 사이의 상태 전이를 P-code에서 요약하고, 다른 바이트코드 위치에 적용하는 방향이다. 첫 관문은 수치 처리 한 경로의 읽기·쓰기·다음 코드 포인터를 매개변수화해, 요약을 동결한 후 다른 즉시값에서 재사용하는지 판정한다. 슬롯·위치 변경과 두 번의 합성은 확장 관문으로 분리한다. 이 설계의 성공을 전체 Lua 프로그램 분석 성공으로 해석하지 않는다.
