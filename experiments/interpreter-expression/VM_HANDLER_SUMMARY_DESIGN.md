# VM 처리 구간 요약 설계와 다음 실험

상태: 설계. 이 문서는 기존 [입력 출처와 한 경로의 계산식 실험](INPUT_PROVENANCE_RESULT.md)을 바탕으로 Astra와 검토한 **Lua 첫 적용 계획**이다. 요약의 핵심 스키마는 [언어 중립 공통 전이 형식](COMMON_VM_TRANSITION_FORMAT.md)에 정의한다. 아래의 처리 구간 요약은 **아직 구현하거나 검증한 결과가 아니다.** `daasdmlkas`는 읽기 전용으로 사용하고, 새 실험 코드와 결과는 이 저장소에 둔다.

## 왜 분석 단위를 바꾸는가

현재 실험은 `run_lua_chunk` 진입부터 첫 VM 덧셈까지 약 5.3만 네이티브 명령을 진행하고, 미리 고른 P-code 연산 21개를 이어 `X+7`을 얻었다. 바이트코드의 수치 명령 `21`이 VM의 `0x4164b8` 처리 지점으로 분기한다는 것도 확인했다. 이 방식은 입력과 네이티브 연산의 연결을 보여 주지만, 바이트코드나 분기가 늘어날 때마다 경로를 다시 고르면 확장하기 어렵다.

특히 현행 `replay_input_path.py`는 선택하지 않은 중간 명령과 모든 호출·메모리 쓰기를 재생하지 않는다. 생략 구간 뒤의 레지스터가 이전 심볼과 **같은 실행값**을 가질 때 관계를 유지하는데, 같은 값으로 다시 정의된 경우는 구별하지 못한다. 지금의 Z3 `unsat`는 선택한 연산의 대수 관계에 대한 결과이며, 처리 구간 전체나 다른 바이트코드의 증명으로 승격하지 않는다.

분석을 두 층으로 나눈다.

1. **엔진 층:** 바이트코드 읽기·분배에서 다음 읽기/반환까지의 네이티브 P-code를 분석해, 한 수치 명령이 VM 상태를 어떻게 바꾸는지 요약한다. 태그 검사나 느린 경로처럼 의미에 필요한 조건은 요약의 사례 조건으로 남긴다.
2. **스크립트 층:** 바이트코드 위치별로 요약을 적용하고 다음 위치를 따라간다. 스크립트의 조건문·반복문에서 생긴 분기를 이 층에서 합치거나 `unknown`으로 보고한다.

엔진 내부의 262개 명령 주소 순서를 매 입력의 적용 조건으로 쓰지 않는 것이 목표다. 실행 조건 자체가 사라지는 것은 아니다. 일반 네이티브 바이너리의 조건문과 마찬가지로, 다른 연산을 수행하는 경로의 조건은 결과식에 남아야 한다.

## 요약의 경계와 내용

현재 확인한 `LOAD(32비트 명령) → INT_AND 127 → BRANCHIND`를 분배 경계 후보로 사용한다. 한 처리 구간은 **분배가 선택한 진입 지점부터 다음 바이트코드 읽기 직전, 반환 또는 해석 불가 종료까지**다. 네이티브 주소의 연속 범위나 소스 수준 Lua opcode 이름으로 정의하지 않는다. 관측된 인덱스 `2→4` 역시 곧바로 규칙으로 넣지 않고, 코드 포인터가 어떻게 변경되는지 P-code에서 구한다.

처리 진입점과 다음 읽기 직전은 서로 다른 종류의 경계다. 요약을 두 번 합성하려면 사이의 `fetch/decode/dispatch` 전이도 모델링하거나, 처음부터 **읽기 직전 → 다음 읽기 직전**으로 맞춘 전이를 만들어야 한다. 처리 진입점의 실제 레지스터와 워드 `W`의 관계도 이 앞단에서 유도해 계약에 넣는다. `W`만 심볼로 두고 이미 해독된 레지스터에 관측값 `7`을 고정하면 재사용 가능한 요약이 아니다.

요약은 반환식 하나가 아니라 상태 전이 계약이다. 첫 표현은 바이트 단위 메모리와 실제 네이티브 레지스터를 보존한다. 슬롯 크기·payload/tag 위치가 접근 주소와 폭에서 입증되면 그 영역을 추상 슬롯으로 승격한다. 소스 수준 `TValue` 레이아웃은 분석 입력으로 주지 않는다. 아래 `W`, `PC`, tag, slot은 **Lua adapter가 공통 상태 위치에 붙이는 binding**이며 공통 스키마의 필수 필드가 아니다.

```text
identity: ELF/Bundle 해시 + 분배 경계 + 처리 진입점
inputs:   32비트 명령 워드 W, 바이트코드 포인터 PC,
          경계에서 살아 있는 네이티브 레지스터, 바이트 단위 메모리 M
entry:    fetch/decode P-code에서 유도한 W ↔ live-in 레지스터 관계
case:
  condition: W의 분배 값과 P-code에서 유도한 태그/분기 조건
  reads:     주소식, 폭, 출처
  writes:    주소식, 폭, 값 식, 보존되는 영역
  next_PC:   P-code에서 유도한 다음 명령 주소식
  exit:      다음 fetch 직전의 cutpoint ID | 반환 | 호출 | unknown(reason)
  evidence:  P-code 주소·ordinal, 가정, 검증 수준
```

현재 숫자 `21`의 정수 덧셈 경로에서 기대하는 **후보 모양**은 아래와 같다. `operand_address`, `decode_immediate`, `next_PC`의 식과 쓰기 범위는 실제 P-code에서 유도해야 하며, `7`이나 관측한 힙 주소를 고정해서 넣지 않는다.

```text
if dispatch_value(W)=21 and operand_tag=3 and other_path_conditions:
    payload' = add64(payload, sext64(decode_immediate(W)))
    update destination payload/tag, next_PC and any other proven effects
else:
    unknown(reason) until that case is analyzed
```

한 번의 메모리 읽기에서 주소가 다르게 관측됐다는 이유만으로 두 주소의 비별칭을 단정하지 않는다. 부분 바이트 쓰기, 중간 쓰기, 호출 효과, 살아 있는 레지스터를 추적해야 한다. 알 수 없는 쓰기가 읽기와 겹칠 수 있거나 호출 효과가 불명확하면 해당 사례는 `unknown`으로 내려간다. 루프와 미해결 간접 분기도 첫 단계에서는 명시적인 한계로 둔다.

`daasdmlkas`의 Bundle, SSA, backward slice 및 기존 출처·부채 보고는 관련 P-code와 의존 후보를 찾는 데 재사용한다. 그 그래프의 의존 집합만으로 피연산자 순서, 분기 방향, 메모리 별칭, 처리 구간의 모든 효과가 해결됐다고 가정하지 않는다. 새 식/전이 결과는 R4interpreter에 별도 층으로 둔다.

## 요약을 얻고 사용하는 절차

1. 기존 추적은 분배 지점과 상태 경계 후보를 찾는 데 사용한다. 분석할 수치 처리 진입점을 seed로 지정했다는 사실을 결과에 기록한다. fetch/decode의 P-code를 따라 `W`와 진입 레지스터의 관계를 먼저 만든다.
2. **첫 관문에서는 관측한 정수 fast 경로의 진입부터 종료까지 P-code와 분기 조건을 빠짐없이 순서대로 처리한다.** 선택한 21개 연산만 건너뛰며 잇지 않는다. 방문한 모든 정의·읽기·쓰기와 별칭 가능한 메모리 버전을 처리하거나 `unknown(reason)`으로 멈춘다. 다른 CFG 경로까지 요약했다고 주장하지 않는다.
3. 바이트코드 워드 `W`, payload, 주소 베이스를 심볼로 두고 이 경로의 조건, 읽기/쓰기, 다음 PC를 계산한다. opcode 분배 값만 해당 case로 제한하고 즉시값·슬롯 인덱스·바이트코드 위치는 매개변수로 남긴다. P-code effect 분석이나 검증용 접근 계측으로 **일시적 쓰기까지 포함한** 메모리 접근 목록을 확인한다. 경계 snapshot은 최종 상태를 비교하는 용도로 쓴다.
4. 요약을 파일로 동결하고, 다른 바이트코드에 적용할 때 다시 추적한 PC나 상수를 보고 코드를 고치지 않는다. 검증 계측은 경계 상태와 전체 관측 메모리 효과를 비교하는 데만 사용한다.
5. 이후 CFG의 다른 분기를 제한적으로 탐색해 추가 case를 만들고, 결과 수준을 `candidate`, `differentially validated`, `proved under preconditions`로 구분한다. 여러 입력의 일치는 검증 결과이며, 모든 가능한 입력·주소에 대한 증명은 아니다.

장기적으로 스크립트 층의 상태는 `(바이트코드 PC, 호출 문맥, 추상 VM 상태)`로 관리한다. 같은 위치로 합류한 호환 상태는 `ite` 또는 SSA phi로 합치되, 메모리 효과와 적용 조건을 보존한다. 루프는 증명된 불변식이나 명시한 유한 범위가 없으면 `unknown(loop bound)`으로 남긴다.

## 다음 **작은** 실험: 같은 수치 처리 구간 재사용

먼저 수치 분배 값 `21`의 **정수 fast 경로 한 개**를 대상으로 한다. 전체 handler CFG나 Lua 프로그램의 식 복원을 첫 성공 기준으로 삼지 않는다.

1. 현재 `x+7` 바이트코드와 ELF/Bundle을 기준으로 분배 진입점, 다음 fetch 경계, 살아 있는 상태와 필요한 메모리 영역을 정한다. fetch/decode와 정수 fast 경로의 모든 P-code를 재생해 아직 모델링하지 못한 쓰기/호출을 목록화한다.
2. 같은 컴파일러로 즉시값을 바꾼 `x+11`을 **평가용 fixture**로 만든다. 소스는 fixture 제작과 출력 정답에만 쓴다. 실제 분배 값을 ELF/P-code와 추적으로 확인한다. 다른 분배 지점으로 간다면 범위 밖으로 보고하고 `21` 요약에 억지로 맞추지 않는다.
3. `x+7`에서 만든 조건부 요약을 먼저 파일로 동결한다. 이 파일에 `x+11`의 `W`, payload, 경계 상태를 넣어 결과 payload/tag, 모든 접근·쓰기, 다음 PC를 예측한다. 새 바이트코드의 trace를 식 추출이나 주소/상수 패치에 사용하지 않는다.
4. 진입/종료 경계 snapshot과 프로그램 실행 결과를 수집해 최종 값을 대조한다. 메모리 접근 계측으로 일시적 쓰기를 포함한 footprint를 별도로 대조한다. `0`, 양수, 음수, 64비트 래핑 경계를 포함한다. 요약 API에 범위 밖 태그를 한 번 넣어 숫자식 대신 `unknown`을 반환하는지도 확인한다.

### 첫 관문: 즉시값이 다른 두 파일

| 판정 항목 | 통과 기준 |
|---|---|
| 재사용 | 같은 요약 해시로 실제 numeric handler `21`에 분배된 `x+7`, `x+11`을 예측. 두 번째 파일에서 재추출·주소 패치·상수 패치 0회 |
| 값·주소 | 파일별 최소 8개 payload와 래핑 경계에서 payload/tag, 다음 PC, 주소식의 예측 오류 0건 |
| 효과 | 선택한 경로의 **모든** 메모리 접근·정의를 모델링하고 일시적 쓰기까지 검증 계측과 대조. 미지원 효과가 남으면 그 사례는 `unknown`이며 이 관문 미통과 |
| 조건 | 경로의 분기 조건을 식으로 보존. 범위 밖 태그 1건을 요약 API에 넣어 `unknown` 확인 |
| 비용 | 요약 추출 비용과 새 입력·파일당 적용 비용을 별도 기록. 새 사례마다 약 5.3만 네이티브 명령을 다시 추적해 식을 만들면 재사용 실패 |

`x+11`이 같은 numeric handler로 분배되지 않으면 그 이유를 기록하고 첫 관문을 통과했다고 하지 않는다. 요약이 정수 case 밖에서 `unknown`을 반환하는 것은 정상이나, 정의한 정수 case 안에서 값·효과가 틀리면 실패다. 이 관문은 **즉시값 변경에 대한 조건부 경로 재사용**만 확인한다.
검증 대상인 두 파일의 정상 정수 사례 최소 16건은 모두 정의된 전이를 산출해야 한다. 이 사례 중 하나라도 `unknown`이면 첫 관문은 미통과로 기록한다.

### 확장 관문: 위치·슬롯과 두 번 적용

세 번째 바이트코드에서 명령 위치와 슬롯을 바꾸고 같은 numeric handler로 실제 분배되는지 확인한다. 재추출·패치 없이 같은 요약의 주소식, 값, 다음 PC를 검증한다. 같은 handler를 두 번 쓰는 바이트코드에서는 첫 종료와 다음 진입 사이의 `fetch/decode/dispatch` 전이를 별도로 모델링한다. **첫 예측 상태와 이 연결 전이에서 두 번째 입력을 계산**한 뒤 요약을 다시 적용한다. 두 번째 진입의 실제 snapshot을 그대로 새 입력으로 넣는 것은 합성 통과로 세지 않는다. 이를 마친 뒤에만 두 번의 전이 합성을 주장한다.

확장 관문까지 통과해도 입력 전역 읽기, 반환, 다른 numeric opcode 및 전체 스크립트 CFG는 별도 작업이다.

## 그 다음 순서

1. 입력 바인딩과 반환 처리의 요약을 추가해 여러 handler를 거치는 최종 출력식을 합성한다.
2. 다른 산술 처리 구간을 요약해 `x+K` 외의 연산에도 같은 P-code·상태 표현을 적용한다.
3. 조건 분기가 있는 바이트코드에서 두 스크립트 경로를 `ite`로 합치고 비용·`unknown` 범위를 잰다.
4. 그 후에 짧은 루프와 메모리 객체/호출 효과를 순서대로 확장한다. VMP는 별도 난독화 분석 단계로 남긴다.
